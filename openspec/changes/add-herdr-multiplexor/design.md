### 1.2 Data/control flow (one Ghostty launch with Herdr installed)

1. **Shell starts** (zsh by default on Omarchy, fish if user ran `chsh -s $(which fish)`).
2. **Zsh init chain**: p10k sources → guard block reads (interactive? unset guard vars? herdr alive?).
3. **Zsh guard hit**: `exec herdr` — the shell process is replaced. No fork, no extra frame, no return.
4. **Herdr takes TTY**: Herdr's controlling terminal is the Ghostty PTY. Herdr sets `HERDR_ENV` for child shells (its paned shells).
5. **User opens a Herdr pane (e.g. press Enter)**: a child shell starts inside Herdr's PTY. The guard sees `HERDR_ENV` set → no nested start. Plain shell (colors + keybindings inherited).
6. **User presses `Ctrl+a N`**: Herdr invokes the wrapper via its `bind` equivalent (keybinding rewrite in `herdr/config.toml` may differ — see REQ-5). The wrapper re-checks liveness, execs a new Herdr/Tmux session with the user-supplied name.

## 3. Wrapper script design (`HatLinux/scripts/ghostty-multiplexer-new`)

### 3.1 FULL file content preview

```sh
#!/bin/sh
#
# ghostty-multiplexer-new — HatDots multiplexer-aware session starter.
#
# Invoked by:
#   - HatLinux/ghostty/config (command = ...)
#   - HatLinux/tmux/.tmux.conf   (bind N command-prompt ... run-shell ...)
#
# Arity: one OPTIONAL positional session name; default = "main".
# Extra args are ignored (intentional; matches the legacy ghostty-tmux-new arity).
#
# Behavior:
#   1. If `herdr` is on PATH and responds to `herdr --version` (liveness probe),
#      exec into it, passing the optional session name through.
#   2. Else if `tmux` is on PATH, exec `tmux new-session -A -s "$SESSION"`.
#   3. Else warn to stderr and exec $SHELL.
#
# Guards (interactive shell only): callers (Zsh/Fish guards) already check
# HERDR_ENV, TMUX, ZELLIJ. This wrapper does NOT re-check those — it is the
# launcher, not the policy. Policy lives in shell init scripts.
#
# Why /bin/sh not bash not zsh: POSIX sh is the lowest common denominator
# among Linux, macOS, WSL, and Ghostty's default PATH. exec semantics and
# command -v are POSIX. This script has no bashisms.
#
# Why no signal handlers: exec replaces the process. A trap is only meaningful
# if we forked a child (we do not). The only failure mode is exec returning,
# which cannot happen unless the binary itself is missing (handled above).

set -eu

SESSION_NAME="${1:-main}"

# --- Herdr liveness probe ---
# `command -v` checks PATH resolvability; `--version >/dev/null 2>&1` skips
# dead shims (R-6). If herdr fails liveness, fall through to tmux.
if command -v herdr >/dev/null 2>&1 && herdr --version >/dev/null 2>&1; then
    # Trap is for cleanup only IF a hypothetical backgrounded job existed.
    # In our wrapper there is no fork; this trap is a future-proofing no-op.
    trap 'exit 1' TERM INT HUP
    exec herdr "$SESSION_NAME"
fi

# --- Tmux fallback ---
if command -v tmux >/dev/null 2>&1; then
    trap 'tmux kill-session -t "$SESSION_NAME" 2>/dev/null || true; exit 1' TERM INT HUP
    exec tmux new-session -A -s "$SESSION_NAME"
fi

# --- Last resort: launch the user's shell with a warning ---
printf 'ghostty-multiplexer-new: no herdr or tmux on PATH — launching $SHELL\n' >&2
exec "${SHELL:-/bin/sh}"
```

### 3.2 Design rationale (per axis)

| Axis | Choice | Rationale |
|---|---|---|
| **Shebang** | `#!/bin/sh` | DG-9. Lowest-common-denominator. execline, dash, busybox sh all qualify. No bash or zsh feature dependency. The existing `HatLinux/tmux/scripts/ghostty-tmux-new` uses `#!/bin/zsh` — we deliberately do NOT match it because: (a) wrapper must outlive `zsh` being absent (Fish-only user), (b) wrapper is invoked by Ghostty which has no concept of user's `$SHELL`, (c) zero feature need for bash-isms. |
| **`set -eu`** | yes | `-e` for fail-fast (catches typos / bind errors); `-u` for unset-var strictness; we do NOT add `-o pipefail` because there are no pipelines. |
| **`$1` handling** | `"${1:-main}"` | POSIX parameter expansion, matches DG-7. |
| **Herdr liveness probe** | `command -v herdr && herdr --version >/dev/null 2>&1` | Two-step: PATH check + executable health. Per R-6: a stale shim on PATH that returns 127 on `--version` must not be exec'd. `--version` is the Herdr CLI convention (REQ-1 evidence). |
| **Tmux invocation** | `tmux new-session -A -s "$SESSION_NAME"` | `-A` (attach-or-create) preserves the existing HatDots behavior (REQ-2). No `-f` flag because the wrapper is called from inside an already-running tmux OR a fresh Ghostty that should load the user's `~/.tmux.conf` itself (tmux sources it by default). |
| **PATH inheritance** | inherit | Ghostty sets PATH for child processes (R-10). The wrapper does no `export PATH`. `command -v` runs in the inherited environment. If Herdr is in `~/.cargo/bin` and the user has sourced cargo in `.bashrc` (which Ghostty does NOT), the user must ensure Herdr is on a PATH Ghostty sees. This is the same constraint as for `tmux-session-layout`. |
| **Signal handling** | TRAP on `TERM INT HUP` | DG-10. Rationale: `exec` replaces the process; signals from a parent (e.g. Ghostty closing) propagate to whichever binary became the new process. The trap is forward-looking (if the wrapper ever forks a probe subprocess) and graceful-degradation: if exec fails (e.g. `herdr` is now uninstalled between liveness probe and exec), the trap kills any partially-set tmux session. The kill-session is best-effort with `2>/dev/null`. |
| **Error handling** | warn + drop into `$SHELL` | Last-resort path (DG-7): user gets a usable prompt even if both multiplexers are absent. Stderr message is one line, terse, no emoji (we are in a terminal-wide session where emoji render inconsistently). |
| **Exit codes** | inherited from exec'd binary | We do not invent new exit codes. If `herdr` exits non-zero, the wrapper exit code is the same. If we drop into `$SHELL`, the wrapper exit code disappears (replaced by the shell). |

### 3.3 Implementation notes (apply-phase hints)

- File mode after creation: `0755` (`chmod +x` in repo).
- The file MUST be a valid POSIX sh script. Validate with `sh -n HatLinux/scripts/ghostty-multiplexer-new` after creation.
- `command -v herdr` should run silently (stdout suppressed with `>/dev/null`). Liveness probe writes stderr to `/dev/null` too (Herdr's `--version` output, if any, is not for us).
- If the user has a `~/.local/bin/herdr` shim (common when `cargo install` puts binaries there without re-sourcing cargo env), the wrapper still works because Ghostty inherits the user's `.profile` which puts `~/.local/bin` on PATH. Confirmed in REQ-1 rationale.

### 4.4 `status is-interactive` placement

`status is-interactive` is checked at TWO places:
- Top-level (Fisher bootstrap): always runs in interactive shells.
- Inside the multiplexer guard: redundant (we already know we're in an interactive shell because the guard itself is conditional on it), but kept for symmetry with Zsh's `[[ -o interactive ]]` check (DG-5 verbatim).

This is intentionally defensive: a Fish user running `fish -c "starship init fish"` would not want the guard to trigger. The `status is-interactive` block ensures the guard is evaluated only when the whole file is sourced in an interactive session.

- **Termux branch**: commented out.

## 5. Zsh `.zshrc` integration

### 5.1 Insertion point

After the powerlevel10k sourcing block (currently lines 22–28 of the existing `.zshrc`). Specifically:

```
[ existing line 25: fi ]    ← ends p10k sourcing block
[ existing line 26: # Cargar configuración de p10k ]
[ existing line 27: [ -f "$HOME/.p10k.zsh" ] && source "$HOME/.p10k.zsh" ]
                                              ← INSERT GUARD BLOCK HERE
```

The block is placed AFTER p10k is fully sourced because:
1. If the user execs into Herdr, p10k never finishes drawing — but if we place the guard BEFORE p10k, then a Herdr-fallback-to-no-multiplexer startup would have a broken prompt. By sourcing p10k first and THEN guarding, we ensure the prompt is ready if the guard falls through (REQ-8 placement rationale).
2. The Herdr PTY swap happens AFTER p10k is initialized → reduced chance of the gitstatusd race in R-1.

### 5.2 Exact insertion (full block)

```zsh
# --- Multiplexer auto-start: Herdr > Tmux > nothing ---
# Guard vars HERDR_ENV, TMUX, ZELLIJ must all be unset.
# See openspec/changes/add-herdr-multiplexor/spec.md DG-5 for parity with Fish.
if [[ -o interactive ]] && [[ -z "$HERDR_ENV" && -z "$TMUX" && -z "$ZELLIJ" ]]; then
    if command -v herdr >/dev/null 2>&1 && herdr --version >/dev/null 2>&1; then
        exec herdr
    elif command -v tmux >/dev/null 2>&1; then
        tmux new-session -A -s main
    fi
fi
```

### 5.3 Why this interacts well with p10k

- p10k gitstatus is a daemon (`gitstatusd`) that opens a PTY-pair-ish file descriptor to monitor repo state. Herdr ALSO opens PTYs for its paned shells. The PTY handoff happens once per Herdr session — not per shell.
- If `herdr --version` liveness probe passes AND `HERDR_ENV` is unset, the very first exec into Herdr happens. p10k gitstatus may attempt one handshake that fails silently (R-1), after which p10k falls back to plain `git status` (slower but working). This is acceptable per REQ-13.
- If gitstatus is broken in practice, the escape hatches are already documented in the existing `.zshrc`:
  ```
  # typeset -g POWERLEVEL9K_VCS_DISABLED=true
  ```
  and the apply-phase README will mention `POWERLEVEL9K_DISABLE_GITSTATUS=true` as the alternate flag (R-9).

## 6. Ghostty config diff (`HatLinux/ghostty/config`)

### 6.1 EXACT line replacement

```
- command = /usr/bin/tmux -f ~/.tmux.conf new-session -A -s main
+ command = ~/.local/bin/ghostty-multiplexer-new main
```

### 6.2 Why this exact form

- Path = `~/.local/bin/ghostty-multiplexer-new` (not absolute `/home/hat/.local/bin/...`). Reason: Ghostty expands `~` at config-load time. Using absolute path freezes the install to one user. `~/.local/bin/...` is portable across user accounts on the same machine and matches the XDG conventions.
- The `main` literal is the default session name, hardcoded because the Ghostty `command =` directive is single-use — there is no per-window session-name argument mechanism in Ghostty config. The default `main` matches DG-7 and REQ-7-arity (the wrapper still accepts `$1` if invoked directly).
- REQ-6: "the Ghostty config SHALL NOT contain the string `tmux` in the `command =` directive" — confirmed by the diff above. (`tmux` strings elsewhere in the file, e.g. `# Usar tmux como shell`, are comments and OK.)

### 6.3 Caveat — link-linux.sh generates the LIVE config

`link-linux.sh` (line 109 in current version) writes `~/.config/ghostty/config` from a heredoc on first install IF the file does not exist; if it exists, link-linux.sh leaves it alone. So:

- For a user running `link-linux.sh` on a CLEAN install, their `~/.config/ghostty/config` will get the old `command = /home/hat/.local/bin/tmux-session-layout main` line. The in-repo edit to `HatLinux/ghostty/config` has NO effect on them.
- For an existing user (who already has `~/.config/ghostty/config`), link-linux.sh does not touch the file.

**Therefore the README migration step (DG-11) must say:**

```bash
# Replace your installed ghostty config with the new repo version:
ln -sfn ~/projects/HatDots/HatLinux/ghostty/config ~/.config/ghostty/config

# Link the wrapper into ~/.local/bin/:
mkdir -p ~/.local/bin
ln -sfn ~/projects/HatDots/HatLinux/scripts/ghostty-multiplexer-new ~/.local/bin/ghostty-multiplexer-new

# Link Herdr config:
mkdir -p ~/.config/herdr
ln -sfn ~/projects/HatDots/HatLinux/herdr/config.toml ~/.config/herdr/config.toml

# Link Fish config (after backing up any existing one — see migration header):
ln -sfn ~/projects/HatDots/HatLinux/fish/config.fish ~/.config/fish/config.fish

# Remove stale ghostty-tmux-new symlink (R-3 cleanup):
rm -f ~/.local/bin/ghostty-tmux-new
```

This is the only way the change is visible to existing HatDots users without touching `link-linux.sh` (C-2 constraint).
